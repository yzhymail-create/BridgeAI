# 需求说明：Muse → 微信 ClawBot 桥接

## 一、目标

手机微信私聊发文字、图片、文件任务，Muse 实际用工具执行，结果回微信，全程中文。
本程序只做微信消息收发，不执行任务；执行由外部 worker（主聊天里的 Muse）完成。

## 二、协议依据

腾讯 openclaw-weixin 协议文档（已全文读过）：
https://github.com/tencent/openclaw-weixin/blob/HEAD/docs/protocol_zh_CN.md

- 域名：`https://ilinkai.weixin.qq.com`（iLink 官方通道，本人绑定流程）
- `channel_version`：`3.0.1/muse-bridge-1.0.0`
  （前三段须是 openclaw-weixin 版本格式，自家版本放后缀，协议允许）
- `bot_agent`：`MuseBridge`
- `iLink-App-ClientVersion`：版本按 `0x00MMNNPP` 编码转十进制，3.0.1 → 196609
- `X-WECHAT-UIN`：随机 uint32 的十进制字符串再 base64 编码

## 三、接口清单

| 步骤 | 方法与路径 | 要点 |
| --- | --- | --- |
| 取二维码 | POST `/ilink/bot/get_bot_qrcode?bot_type=3` | 请求体只有 `local_token_list`；首次登录传空数组。响应 `qrcode`（轮询用）与 `qrcode_img_content`（展示用） |
| 轮询扫码状态 | GET `/ilink/bot/get_qrcode_status?qrcode=...` | 长轮询，单次 35 秒；PIN 放下次轮询的 `verify_code` |
| 收消息 | POST `/ilink/bot/getupdates` | 游标 `get_updates_buf`；服务端建议超时 35000ms |
| 发消息 | POST `/ilink/bot/sendmessage` | 文本 `message_type` 2、item type 1；图片 type 2、文件 type 4；回复带入站 `context_token` |
| 取上传参数 | POST `/ilink/bot/getuploadurl` | 媒体上传前取 `upload_full_url` 或 `upload_param`（见 §十四） |
| 上传密文 | POST 上传 URL（CDN） | `Content-Type: application/octet-stream`；成功判定是 HTTP 200 且响应头 `x-encrypted-param` 非空 |
| 下载媒体 | GET `<cdn_base_url>/download?encrypted_query_param=...` | CDN 地址；图片/文件下载解密后落盘（见 §十四） |

请求头（鉴权 POST）：`Content-Type: application/json`、
`AuthorizationType: ilink_bot_token`、`Authorization: Bearer <token>`、
`X-WECHAT-UIN`、`iLink-App-Id: bot`、`iLink-App-ClientVersion`；
请求体带 `base_info{channel_version, bot_agent}`。
取二维码的 POST 不带 `Authorization` 与 `base_info`；
状态轮询 GET 只带应用请求头（`iLink-App-Id`、`iLink-App-ClientVersion`）。

## 四、二维码规则（成败关键）

1. `qrcode_img_content` 可能是微信 liteapp 登录页网址而不是图片：
   先判断——下载能拿到图片字节则直接用；否则直接把这个网址本身编成二维码 PNG。
2. 绝不能静默退回只编 32 位 `qrcode` token；`qrcode_img_content` 为空直接报错。
3. 生成后必须用 OpenCV `QRCodeDetector` 解码核对：自编的解出内容必须一字不差
   等于预期载荷；服务端图片必须能解出非空内容；否则拒绝展示并报错。
4. 每张二维码用唯一文件名（时间戳 + 随机后缀），存 `state/qr/`，不叫 `qr.png`。
5. 二维码有效期很短（协议没给数字，外部实测说法 1–5 分钟不一），拿到马上扫。
6. 过期不自动重生成，不自动循环登录流程。

## 五、登录与 PIN

- `login` 只取二维码，不等扫码结果；`wait-login` 轮询状态。
- `wait-login` 单次长轮询 35 秒，总超时 60 秒。
  注意：60 秒是本项目自定的取值，不是协议规定。
- 状态：`wait` 继续等；`scaned` 已扫码；`confirmed` 保存凭证；
  `expired` / `verify_code_blocked` 报错停止；`scaned_but_redirect` 按
  `redirect_host` 切换轮询地址；`binded_redirect` 用已有凭证视为已连接。
- `need_verifycode` 时暂停等 PIN：每轮检查 `state/pin.txt`（0600），
  有则读出、下次轮询带 `verify_code`、用后立即删除；没有就继续等（总超时内）。
- 凭证原文存 `state/session.json`，权限 0600：
  `bot_token`、`ilink_bot_id`、`baseurl`、`ilink_user_id`。

## 六、收消息与过滤（serve）

- 单实例：`state/serve.lock`，第二个实例直接退出报错。
- 长轮询 `getUpdates`，游标持久化到 `state/cursor.json`，只在返回非空时更新。
- 按 `message_id` 去重，已处理 ID 持久化在 `state/processed.json`（最多 5000 条）。
- 只处理扫码绑定用户（`from_user_id == session.ilink_user_id`）的私聊
  （`group_id` 为空）；群消息、其他用户消息、机器人自己的消息
  （`message_type == 2`）直接忽略，不记录任务。
- 文本消息写 `inbox/<message_id>.json`，状态 `received`。
- 图片（type 2）与文件（type 4）消息已接入：下载解密后落盘到
  `inbox/media/<message_id>/`，inbox 记录里记相对路径
  `media/<id>/<文件名>`，状态 `received`；图文混合记为 `mixed`。
  无文本且媒体全下载失败时回固定文案
  “刚才的图片/文件没能下载下来，请再发一次”，HTTP 成功即记 `sent`。
- 语音（type 3）、视频（type 5）等未接入类型立即用 `sendMessage`
  回固定文案“语音和视频暂时还不能处理，请先用文字描述”，
  HTTP 成功即记 `sent`（不假装读过内容）；只有发送报错才记 `pending-send`。
  语音回不了是微信侧协议限制（无回语音的路子），不是本程序没接。
- `ret == -14`（或 `errcode == -14`）表示会话过期，serve 停止，需重新登录。
- serve 只收不执行任务。

## 七、发消息（send-once 为正式入口）

- 正式发送只用 `send-once <message_id>`：自己读 inbox（收件人、令牌）与
  outbox（回复文本），查状态→发消息→记 `sent` 全程加状态锁
  （`state/status.lock`，可重入，最多等 30 秒）。
- 媒体回复走同一口子：worker 把文件放进 `outbox/`，再写清单
  `outbox/<message_id>.media.json`（`{"type": "file"|"image", "file": "<纯文件名>",
  "caption": "可选说明文字"}`）；`send-once` 有清单时发媒体，
  无清单时走文本。查状态、发媒体、记 `sent` 同样在同一把锁里完成，
  防重发规则与文本一致；清单里的 `file` 必须是纯文件名，带路径直接拒绝。
- 防重发原理：2026-11-22 实测两条回复都发了两遍，根因是 hook worker 与主聊天
  各发了一次（单次 POST 本身不重复，hook 每条消息只唤醒一次，代码与日志已核实）。
  `pending-send` 状态分不清“已发未确认”与“还没发”，只靠查状态防不住；
  所以查、发、记必须在同一把锁里完成，已是 `sent` 的直接跳过。
- HTTP 成功即记 `sent`，不等 `ret`：微信经常不回 `ret`，2026-11-22 实测
  两次发送都只回 HTTP 200、无 `ret`，用户在微信里都收到了。
  不要留 `pending-send` 等确认，不要让用户在微信里确认收到。
- 只有命令报错（网络不通、非零 `ret`、凭证失效）才算失败，留在
  `pending-send` 并写清原因，允许重试。
- 每次发送都在 `logs/bridge.log` 记一条（只记字数与结果，不记内容）。
- 底层 `send` 命令只做单次发送、不查状态，日常不要直接用。

## 八、状态机

`state/status.json` 按 `message_id` 记录：

```
received → executing → pending-send → sent
```

- `received`：已收到文字/图片/文件任务，等 worker 执行。
- `executing`：worker 正在执行（worker 用 `mark` 命令推进）。
- `pending-send`：结果已生成，正在发回微信；正常情况下不滞留，只有发送报错时才停留等重试。
- `sent`：已发回微信（发送命令 HTTP 成功即记，不等 `ret`）。

`mark <message_id> <新状态>` 供外部 worker 调用。
`send-once` 是唯一正式发送入口：查状态→发→记 `sent` 在状态锁里一次完成。

## 九、唤醒机制

`serve` 把任务写进 `inbox/` 后，由 hook 每 15 秒查一次
`state/status.json` 里有没有 `received` 状态的新消息，有则唤醒 worker 执行，
无则静默。hook 脚本在 `~/hooks/scripts/wechat-inbox-watch.sh`，
登录成功后才注册启用。不要同时跑 `serve` 和别的轮询抢同一个游标。

## 十、脱敏

- token、`qrcode` 值、二维码载荷原文只存 `state/session.json` 与
  `state/login_session.json`（0600），绝不写进日志、聊天输出或其他文件。
- AES 密钥（aeskey）、CDN 上传参数（upload_param）、下载参数
  （encrypt_query_param）同样是敏感值：上传/下载时登记进脱敏器，
  绝不写进日志或 inbox 记录。
- 所有日志输出前过 `redact()`，`Authorization: Bearer` 兜底抹掉。
- `status` 命令不输出任何凭证。

```
├── state/               # 凭证/游标/状态/锁/二维码（git 排除，勿动凭证文件）
├── inbox/               # 收到的任务（git 排除）；图片/文件落盘在 inbox/media/<id>/
├── outbox/              # 待发结果（预留，git 排除）；媒体回复的清单与文件也放这里

```

## 十二、恢复方法

- 虚拟机替换：后台 serve 不能保证存活。恢复 = 重新启动 serve
  （凭证在 `state/session.json`，随 home 目录持久化，不用重新登录）；
  hook 由系统恢复后继续每 15 秒检查 inbox。
- serve 异常退出：查 `logs/bridge.log`，确认旧进程已死后重新启动；
  锁文件残留时先确认无 serve 进程，再删 `state/serve.lock`。
- 会话过期（日志出现 `-14`）：重新登录（`login` + `wait-login`）。
- 二维码过期：重新运行 `login` 生成新的（不会自动重生成）。
- 游标丢失：删 `state/cursor.json` 后重启 serve，会从头拉取，
  去重机制保证已处理的消息不重复进 inbox。

## 十四、图片与文件收发

协议依据：腾讯 openclaw-weixin 源码 `src/cdn/` 与 `src/messaging/send.ts`
（2026-11-22 核对，commit ffc7ae16）；媒体逻辑放 `media.py` 单独模块，
`bridge.py` 只调它，不直接碰加密与 CDN 细节。

### 发送（文件与图片同流程）

1. 明文算大小与 MD5；随机 16 字节 filekey 与 16 字节 aeskey。
2. POST `getUploadUrl`，请求体含 filekey、media_type（1 图片、3 文件）、
   to_user_id、rawsize、rawfilemd5、filesize（填充后大小）、
   `no_need_thumb: true`、aeskey（十六进制）。
   响应须含 `upload_full_url` 或 `upload_param` 至少一个，否则报错。
3. 密文大小 = `(明文大小 // 16 + 1) * 16`（AES-128-ECB + PKCS#7 填充，
   标准库没有 AES，用 `pycryptodome`）。
4. 密文 `Content-Type: application/octet-stream` POST 到上传 URL：
   优先用 `upload_full_url`；否则按
   `{cdn}/upload?encrypted_query_param=<upload_param>&filekey=<filekey>` 拼。
   CDN 域名：`https://novac2c.cdn.weixin.qq.com/c2c`。
   最多重试 3 次，4xx 立即失败；成功判定是 HTTP 200 且响应头
   `x-encrypted-param` 非空，取其值作下载参数。
5. 再用 `sendMessage` 发媒体 item，媒体引用三字段：
   `encrypt_query_param`（下载参数）、`aes_key`、`encrypt_type: 1`。
   注意：查询参数名是 `encrypted_query_param`（带 ed），
   媒体字段名是 `encrypt_query_param`（不带 ed），别写混。
   `aes_key` 是“十六进制字符串再 base64”（对 32 个十六进制字符做 base64，
   不是直接对 16 字节做 base64）。
   图片 item：`{type: 2, image_item: {media, mid_size}}`，`mid_size` 是密文大小；
   文件 item：`{type: 4, file_item: {media, file_name, len}}`，
   `len` 是明文大小的十进制字符串。
6. 说明文字与媒体拆成独立请求，各用独立 client_id，文字先发；
   每请求 item_list 恰好一项。说明文字发失败时不发媒体。
7. 单个文件上限 100MB（超过直接拒绝，不上传）。

### 接收

- 媒体消息优先用 `full_url`，没有就按
  `<cdn_base_url>/download?encrypted_query_param=<编码后参数>` 构造下载地址。
- 图片解密密钥优先 `image_item.aeskey`（十六进制），其次 `media.aes_key`
  （base64，接受 base64(16 字节原文) 与 base64(32 位十六进制串) 两种形式）；
  无密钥的图片按明文处理。文件缺 `media.aes_key` 直接跳过（官方做法）。
- 单个媒体上限 100MB，超过拒绝下载。
- 下载解密后落盘到 `inbox/media/<message_id>/`，inbox 记录里只记相对路径。
- 语音是 SILK 格式（需转码），视频未接入：两者都回固定文案，见 §六。

### 命令与防重发

- 底层命令：`send-media --to <用户ID> --file <本地路径>
  [--type image|file] [--caption "说明文字"] [--context-token <令牌>]`；
  `--type` 不给时按文件头魔数自动判定。
- 正式入口仍是 `send-once` + 媒体清单（见 §七），查状态、发媒体、记 `sent`
  在同一把状态锁里完成，防重发规则与文本一致。
- 真机验收等用户点头再做；不要往用户微信真发图片/文件做测试。
